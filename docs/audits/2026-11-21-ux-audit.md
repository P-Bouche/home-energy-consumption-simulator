# UX Audit — `apps/web` — 2026-11-21

**Scope.** Usability audit of the web app (`apps/web`, React + MUI + Zustand + R3F) for a
French homeowner persona. Docs-only audit: no code changes. Visual styling is out of scope
(a separate visual audit, PR #24 / branch `docs/ui-audit`, covers it); this audit covers
**behavior and information architecture**.

**Primary evidence.** The four client-reported pain points, verified and extended by walking
the app end to end:

1. "Style très dated, trop d'informations affichées" — home page feels overloaded.
2. "Bouton Simulation au milieu de la page" — the key action feels arbitrarily placed.
3. "Affichage 3D pas fidèle à une maison" — the 3D view does not read as a house.
4. "Modification de simulation très dure : il faut connaître le U et plein d'énums du DPE."

## Method

- Clean checkout, `npm ci`, API started with `DATABASE_URL=memory:// npm run start -w apps/api`
  (port 3000), web dev server `npm run dev -w apps/web` (port 5173).
- DPE fixture imported through the real UI: `packages/open3cl-adapter/test/fixtures/2238E0097309E.xml`
  (DPE n° 2238E0097309E).
- Journeys walked in a real browser (Playwright): (a) import DPE → read result,
  (b) edit a wall → read the impact, (c) create/compare renovation scenarios, plus the 3D viewer
  (default view, element selection, hover tooltip, heat-loss overlay). Every screen was
  screenshotted (see Evidence index) and all figures below were cross-checked against the API.
- Source attribution: every finding references the component in `apps/web/src`.

**Verified figures for the fixture** (API cross-check): import report = 86 parsed fields,
3 inferred, **324 unrecognized XML paths**, 3 missing; building = 1 wall, 6 windows, 1 heating
system, 1 ventilation system (roofs/floors are synthesized at geometry time); simulation =
**étiquette Énergie D / Climat D, 202 kWh/m².an, 42 kg CO₂/m².an, 16 400 kWh (5 usages),
3 413 kg CO₂e, moteur Open3CL v1.11.6**; after editing wall-1 U from 1.6393 → 0.2 the building
bumps to version 1 and re-simulates (cache miss).

**Environment caveat.** In this sandbox, Chromium is killed by the OS whenever a text `<input>`
renders, so form screens were captured in headless Firefox and the WebGL viewer in headless
Chromium (SwiftShader). The screenshots are real captures of the running app; content quoted in
this report is from the source and the live DOM.

## Findings

### F1 — Blocker — Editing a wall requires expert knowledge (U-value, raw DPE enum ids)

- **Journey / screen:** (b) edit a wall → `BuildingEditorPanel` edit dialog; same pattern in the
  scenario form.
- **Evidence:** [ux-08-edit-dialog.png](assets/ux-08-edit-dialog.png),
  [ux-09-edit-invalid-u.png](assets/ux-09-edit-invalid-u.png),
  [ux-12-scenario-form.png](assets/ux-12-scenario-form.png).
  The wall dialog (`apps/web/src/components/BuildingEditorPanel.tsx:50-55`) shows free-text
  fields labeled `U (W/m².K)`, `Orientation (enum id)`, `Type de mur (enum id)`,
  `Adjacence (enum id)`, prefilled with raw DPE codes — for wall-1 the live values are
  `orientation = "2"`, `wallType = "13"`, `adjacency = "1"`. The scenario catalog asks for
  `Type d'installation (id)` with placeholder `4` (`apps/web/src/components/command-catalog.ts:70`).
  Entering `U = -1` returns the engine's English message `must be in (0, 4] W/m².K` verbatim in the
  field helper (ux-09). A homeowner cannot know what U to type nor what enum id 13 means.
- **Recommendation (behavior/IA):** the editor must accept *project language*, not DPE language:
  enum fields become labeled pickers ("Nord", "Mur en béton banché avec doublage", …) with the
  raw id as secondary info; U becomes a guided input (slider with a sane range + numeric fallback +
  plain-language reading of the current value, e.g. "mur non isolé"). Validation messages are
  translated into plain French. See the deep-dive below for sized options.
- **Target state:** to edit a wall the homeowner needs to know **nothing but their own project**
  (which wall, what work they are considering) — no U-value, no enum code.

### F2 — Major — The home page is one dense single-column stack; the import report floods the screen

- **Journey / screen:** (a) import DPE → read the result — `UploadPage`.
- **Evidence:** [ux-02-home-after-import.png](assets/ux-02-home-after-import.png),
  [ux-03-import-report.png](assets/ux-03-import-report.png). After import, `UploadPage.tsx:70-77`
  stacks, in one `Container maxWidth="md"` with no navigation, tabs or stepper: success alert →
  "Voir le modèle 3D" button → import report → simulation panel → editor panel → scenario panel.
  The import report (`ImportReportView.tsx`) lists every parsed field (86), every inferred field,
  **all 324 unrecognized XML paths one by one** (`ImportReportView.tsx:86-98`), and missing fields,
  each with raw XML paths like `dpe/logement/enveloppe/mur_collection/mur[1]/...`.
- **Recommendation (IA):** after import, land on a **summary screen**: DPE label/figures, the few
  fields that are missing or inferred (with their confidence, in plain words), and clear entries to
  the 3D view, the simulation and the editor. The full field-by-field report stays available behind
  an explicit "voir le détail de l'import" action; unrecognized paths are collapsed to a count with
  an expandable list.
- **Target state:** the homeowner reads "your DPE says D, 202 kWh/m².an; 3 values were estimated,
  here they are" — and nothing else until they ask for more.

### F3 — Major — "Lancer la simulation" is one button buried mid-page; the result appears below it

- **Journey / screen:** (a) run the simulation — `SimulationPanel`.
- **Evidence:** [ux-02-home-after-import.png](assets/ux-02-home-after-import.png),
  [ux-04-simulation-panel-idle.png](assets/ux-04-simulation-panel-idle.png),
  [ux-05-simulation-result.png](assets/ux-05-simulation-result.png),
  [ux-06-simulation-raw-output.png](assets/ux-06-simulation-raw-output.png).
  The run button (`SimulationPanel.tsx:97-99`, `Lancer la simulation`) sits inside the third panel
  of the long page; the result (labels, chips, detail line, raw-JSON toggle at
  `SimulationPanel.tsx:55`, history at `:128`) renders below the button inside the same panel, so
  the outcome is below the fold.
- **Recommendation (behavior/IA):** make "Lancer la simulation" the **primary, always-visible
  action of the building view** (e.g. pinned in the view header) and show the latest result as a
  **summary at the top** of the building view (label badges + kWh/m².an + CO₂), with the detail,
  history and raw engine output behind expanders. The raw engine JSON should be opt-in technical
  content, not a default-visible section.
- **Target state:** the homeowner sees their DPE result and can re-run the simulation without
  scrolling; they know they only need to import the DPE to get there.

### F4 — Major — After an edit, the impact is not stated where the edit happened

- **Journey / screen:** (b) edit a wall → read the impact — editor + simulation panels.
- **Evidence:** [ux-10-home-after-wall-edit.png](assets/ux-10-home-after-wall-edit.png),
  [ux-11-editor-after-edit.png](assets/ux-11-editor-after-edit.png). After saving, the editor shows
  `version 1` and an audit row formatted as raw command output
  (`building.wall.update.v1 · v1 · local-user · … | uValueWm2K : 1.6393 [dpe-xml:…, confiance 1] → 0.2 [user, confiance 1]`,
  `BuildingEditorPanel.tsx:147-150, 300-315`). The *impact* (new simulation, Δ kWh, label change)
  only appears as another line in the simulation panel's history list
  (`SimulationPanel.tsx:128-136`) — nothing next to the edit says what changed for the homeowner.
- **Recommendation (behavior/IA):** after each save, show an **impact summary attached to the
  editor** ("Simulation relancée : −X kWh/an, étiquette D → C") computed from the new
  `SimulationResult`, plus a plain-language diff of what changed ("U du mur wall-1 : 1,64 → 0,20").
  The raw audit trail remains available as technical detail.
- **Target state:** the homeowner edits, and immediately reads in plain words what the change does
  to consumption and label — without opening another panel.

### F5 — Major — The 3D view does not read as a house

- **Journey / screen:** 3D viewer — `ViewerPage` + `BuildingModel` + `ElementPanel`.
- **Evidence:** [ux-14-viewer-3d.png](assets/ux-14-viewer-3d.png),
  [ux-15-viewer-element-selected.png](assets/ux-15-viewer-element-selected.png),
  [ux-16-viewer-hover-tooltip.png](assets/ux-16-viewer-hover-tooltip.png),
  [ux-17-viewer-heat-loss.png](assets/ux-17-viewer-heat-loss.png).
  For this fixture the geometry is a flat 10,4 m × 7,9 m × 2,5 m box: 1 wall + 6 windows + a
  synthesized roof/floor/room, **all marked inferred** (hatched overlay), no roof pitch, no façade
  treatment, no north arrow. The header shows the raw UUID (`ViewerPage.tsx:52`, `Modèle 3D — {buildingId}`),
  and the side panel leads with `id : wall-1`, `type : wall` and values with raw sources
  (`ElementPanel.tsx:33-56`).
- **Recommendation (behavior/IA):** the viewer should present the building as a **recognizable
  house**: roof/floor rendered as solid slabs with a pitched-roof option when the DPE has one,
  façade vs. opening colors consistent, a compass/north indicator (orientation matters to homeowners),
  and a default camera framing that shows the whole volume. Element identity should be shown in
  plain words first ("Mur nord — 54 m²", "Fenêtre simple vitrage bois") with the id as secondary.
  Inferred elements should be explainable in one click ("cette paroi a été estimée car absente du DPE").
- **Target state:** the homeowner recognizes their house and its parts by name and orientation;
  they never need to read a UUID or an enum to understand the model.

### F6 — Major — Confidence metadata is shown everywhere as raw technical chips

- **Journey / screen:** (a) import report, (b) editor list, 3D side panel.
- **Evidence:** [ux-03-import-report.png](assets/ux-03-import-report.png),
  [ux-07-editor-list.png](assets/ux-07-editor-list.png),
  [ux-15-viewer-element-selected.png](assets/ux-15-viewer-element-selected.png).
  Every element row shows chips like `DPE (confiance 1)` (`BuildingEditorPanel.tsx:130-145`), and
  the 3D tooltip shows `… — dpe-xml:dpe/logement/… — confiance 1 (inféré)` (`ViewerOverlays.tsx:58`).
  The data-confidence rule is correctly implemented, but surfaced as jargon.
- **Recommendation (behavior/IA):** keep the metadata (it is a project requirement) but render it
  in plain language at the point of decision: "valeur mesurée du DPE" vs "valeur estimée — à
  vérifier", with the confidence score as a subtle indicator, and the raw source path behind a
  "d'où vient cette valeur ?" detail. Aggregate it in the summary screen (F2) instead of repeating
  it on every row.
- **Target state:** the homeowner knows which numbers to trust and which to verify, without
  learning what "confiance 0,7" or a source path means.

### F7 — Minor — Scenario creation reuses the raw command vocabulary; internal tags leak into copy

- **Journey / screen:** (c) create/compare scenarios — `ScenarioPanel`.
- **Evidence:** [ux-12-scenario-form.png](assets/ux-12-scenario-form.png),
  [ux-13-scenario-compare.png](assets/ux-13-scenario-compare.png). The form is command-first: a row
  of selects/inputs per raw command (`ScenarioPanel.tsx:200-250`), target picker showing
  `wall-1 — <description>` (id first), U as a bare number field, heating/ventilation as enum ids.
  The panel title contains the internal phase tag `Scénarios de rénovation (P5)`
  (`ScenarioPanel.tsx:131`). The comparison table itself is well designed (rank, Δ kWh, Δ kg CO₂e,
  label change — verified: wall insulation U 1,64 → 0,2 gives D → C, rank 1) and should be kept.
- **Recommendation (behavior/IA):** scenarios should be **work-first**: "Isolation des murs",
  "Remplacement des fenêtres"… as named actions the homeowner picks, with the target element
  chosen by plain name/location; numeric parameters use the same guided controls as the editor
  (F1). Drop internal phase tags from user-facing copy.
- **Target state:** the homeowner describes the renovation work they are considering; the app
  handles the rest.

### F8 — Minor — Raw identifiers and English engine messages in user-facing text

- **Journey / screen:** global.
- **Evidence:** [ux-02-home-after-import.png](assets/ux-02-home-after-import.png) (success alert
  `Bâtiment importé : <uuid>`, `UploadPage.tsx:57`; building id in `<code>`,
  `SimulationPanel.tsx:88`), [ux-09-edit-invalid-u.png](assets/ux-09-edit-invalid-u.png)
  (English `must be in (0, 4] W/m².K`), [ux-14-viewer-3d.png](assets/ux-14-viewer-3d.png)
  (UUID in the viewer header).
- **Recommendation:** display a human name for the building ("Mon DPE 2238E0097309E") with the id
  in secondary/technical detail; map engine validation messages to French, plain-language
  equivalents (the field, the allowed range in words: "U doit être compris entre 0 et 4 W/m².K").
- **Target state:** no UUIDs or English error strings are the first thing a homeowner reads.

### Positive observations (keep)

- The scenario **comparison table** (rank, deltas, label change) is exactly the right IA for
  comparing renovations ([ux-13](assets/ux-13-scenario-compare.png)).
- Undo + append-only audit trail exist and re-simulate correctly after each edit.
- The heat-loss overlay with its legend works and is a strong feature once a simulation exists
  ([ux-17](assets/ux-17-viewer-heat-loss.png)) — but it silently appears only after a simulation
  has run; that discoverability gap belongs to F3/F5.
- Cached-result badge and simulation history are useful and correct.

## Deep-dive — pain point 4: what the editing experience should become

Current state (F1): every editable field is a raw technical value — `U (W/m².K)`, `Uw`,
`orientation/wallType/adjacencyType/glazingType/frameMaterial/installationType/ventilationType`
as DPE enum ids (`BuildingEditorPanel.tsx:42-113`, `command-catalog.ts`). The homeowner must know
physics (U-values) and the DPE enumeration tables. The engine already owns human labels for these
enums (e.g. `orientation: '2' → 'nord'` in the engine's `enums.d.ts`), reachable only through the
Open3CL adapter — so label mapping is a presentation concern over existing data, not new
calculation.

Sized options (small → large), so the maintainer can pick an ambition level:

- **S — Label and explain (small).** Replace every `enum id` field with an autocomplete whose
  options show the human label ("Nord") with the id in secondary text, labels resolved via the
  adapter from the engine's own enum tables. Prefill plain-language descriptions; add example
  placeholders ("ex. 0,20 pour une isolation par l'extérieur" — already present in the catalog
  descriptions, promote them into the inputs); translate validation messages to French. U stays a
  number, but with a min/max slider bound to the valid range (0–4 W/m².K) and a plain-language
  reading of the current value ("mur non isolé" / "isolation moyenne" / "très bonne isolation")
  based on U thresholds.
- **M — Presets over numbers (medium).** On top of S: replace the bare U input with **preset
  cards per element type** — "Non isolé", "Isolation standard", "Isolation renforcée (rénovation
  globale type 2025)", each mapping to a U range and showing an estimated effect — plus a slider
  inside the chosen band for fine-tuning. Windows become "simple vitrage" / "double vitrage" /
  "double vitrage récent" / "triple vitrage" presets mapped to Uw. Heating/ventilation become
  labeled choices ("Chaudière gaz condensation", "Pompe à chaleur air/eau", "VMC simple flux",
  "VMC double flux"…) mapped to the DPE enum ids. The raw value remains visible in an advanced
  details section.
- **L — Work-first editing with immediate impact (large).** Editing starts from the renovation
  intent, not the element: the homeowner picks a measure card ("Isoler mes murs extérieurs",
  "Changer mes fenêtres", "Isoler ma toiture", "Changer ma chaudière"), then picks *which* element
  (in the 3D view or in a plain-language list: "Mur nord — 54 m²"), then a preset/intensity.
  Each change immediately shows the simulated impact (Δ kWh/an, Δ CO₂, label change — reusing the
  scenario comparison machinery) and an estimated cost band. The current command vocabulary
  (`building.*.update.v1`) stays the internal contract; only the presentation changes.

**Target state (all levels):** to complete an edit, the homeowner needs to know **nothing but
their own project** — which element, what work, roughly what performance level. U-values and DPE
enum codes never appear as required input.

## Prioritized backlog (one-line user stories, severity-ordered)

1. **Blocker** — As a homeowner, I can edit any building element using plain-language labels and presets, without knowing U-values or DPE enum codes.
2. **Major** — As a homeowner, after importing my DPE I land on a summary screen (label, key figures, estimated values flagged in plain words) instead of the raw field-by-field report.
3. **Major** — As a homeowner, "Lancer la simulation" is the visible primary action of the building view and its result summary appears without scrolling.
4. **Major** — As a homeowner, after each edit I see the impact right where I edited (Δ kWh, Δ CO₂, label change in plain words), not only in a history list.
5. **Major** — As a homeowner, the 3D view reads as my house (solid walls/roof, openings, compass, whole-volume framing) with elements named in plain language instead of UUIDs.
6. **Major** — As a homeowner, the 324 unrecognized XML paths of the import report are collapsed to a count, expandable on demand.
7. **Major** — As a homeowner, confidence/source metadata is expressed as "mesuré par le DPE" vs "estimé — à vérifier", not as raw `confiance 0,7` / source-path chips on every row.
8. **Minor** — As a homeowner, all enum fields are autocompletes showing human labels first ("Nord"), with the raw id as secondary information.
9. **Minor** — As a homeowner, validation errors are in French and plain language (e.g. "U doit être entre 0 et 4 W/m².K").
10. **Minor** — As a homeowner, I build scenarios from work descriptions ("Isolation des murs") and pick elements by plain name, not by raw command rows and ids.
11. **Minor** — As a homeowner, I never see internal phase tags ("P5") or raw UUIDs in titles, alerts, or headers.

## Limitations and assumptions

- One fixture walked end to end (2238E0097309E, a single-wall apartment-style DPE with 6 windows);
  findings generalize to other DPEs but a house fixture (roof, multiple walls) was not walked —
  the 3D finding (F5) is partly a consequence of this fixture having no roof in the DPE.
- Screenshots were taken in headless browsers in a constrained sandbox (Firefox for form screens,
  Chromium+SwiftShader for WebGL); they are real captures, but pixel-level rendering may differ
  slightly from a desktop browser.
- No code was changed; all component references are to `main` at commit 65c171e.
- Severity scale: **blocker** = task cannot be completed by the target persona; **major** = task
  completable but with significant friction or risk of misunderstanding; **minor** = polish/clarity.
